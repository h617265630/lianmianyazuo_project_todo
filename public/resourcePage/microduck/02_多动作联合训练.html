02 · 多动作联合训练 —— 怎么让鸭子会很多事

核心答案：每个动作是一个独立的 ONNX 策略，运行时由 daemon 按 slot 切换。

1. 先纠正一个直觉偏差

新人最容易问的问题：

能不能训一个大网络，什么都会？

技术上可以（multi-task / hierarchical RL / skill primitives），但工程上当前不是这么做。原因是：

  1. 训练变慢很多——多个任务共享表征会互相干扰（task interference）
  2. sim2real 难度爆炸——失败模式叠加，调试极其痛苦
  3. 算力不划算——鸭子只有 RK3566（4×A55），单策略 50 Hz 推理已经吃紧

Pollen Robotics 选择的工程方案：每个动作训一个 ONNX，运行时做切换。这就是为什么 microduck 机器人出厂带 7 个独立策略。

2. 官方动作 / 槽位表

来自 src/mjlab_microduck/publish/manifest.py 的 SLOTS 常量：

SLOTS = ("walk", "stand", "sitstand", "ground_pick",
         "kick_left", "kick_right", "roulade")
Slot含义任务 IDkind
walk走路（默认）Mjlab-Velocity-Flat-MicroDuckperpetual
stand站立（专用的站立任务）perpetual
sitstand坐 ↔ 站（按命令切换）Mjlab-SitStand-Flat-MicroDuckperpetual
ground_pick用嘴捡东西Mjlab-GroundPick-Flat-MicroDuckepisodic
kick_left左脚踢球Mjlab-BallKick-Flat-MicroDuckepisodic
kick_right右脚踢球Mjlab-BallKick-Flat-MicroDuckepisodic
roulade前滚翻Mjlab-Roulade-Flat-MicroDuckepisodic

每个 slot 由独立的 PPO 训练得到，权重是一个 ~MB 级别的 ONNX。

3. kind 字段：episodic vs perpetual

perpetual（永久性的）

  • 没有终止时间，一直跑直到 daemon 让它停
  • 走路 / 站立 / sitstand 都是这种
  • daemon 把它们装到 slot 里

episodic（一次性的）

  • 有时间限制 duration_s，到时间自己停
  • 踢球 / 滚翻 / 捡东西都是这种——它们有起手式 + 收势，做完必须让位
  • daemon 用 robotctl robot do <name> 触发
一句话区分：走路是 perpetual，技能是 episodic。

4. 多个 ONNX 在运行时是怎么"联合"起来的

鸭子不是"一个大脑"，而是"一窝专家 + 一个调度员"。

┌─────────────────────────────────────────────────────────────┐
│  robotd (Rust daemon, 50 Hz)                                  │
│  ┌──────────┐    policy_id    ┌──────────────────────────┐   │
│  │ Scheduler │ ──────────────▶ │ 当前激活的 ONNX 推理     │   │
│  │ (state    │                 │ (单线程 onnxruntime)    │   │
│  │  machine) │ ◀──────────────  │                         │   │
│  └──────────┘    ctrl[14]     └──────────────────────────┘   │
│       ▲                                  ▲                   │
│       │ gamepad / NFC / voice / app      │ obs[61]           │
└───────┼──────────────────────────────────┼───────────────────┘

几个关键事实：

  1. 同时只跑一个 ONNX——切换是瞬时的，不是 blend
  2. 切换走"先到位再切"的协议——上一个策略把姿态收完，下一个策略从站立姿态接过去
  3. 观测是 61D 共享的——这是 manifest 强制要求的硬约束
  4. 切换由 daemon 决定，不是策略之间协调——简单可靠

5. 自己加一个新动作的完整流程

假设你想加一个"鞠躬"动作。

5.1 写任务配置

在 src/mjlab_microduck/tasks/ 加 microduck_bow_env_cfg.py

5.2 注册

在 tasks/__init__.py 加一行 register_mjlab_task(...)

5.3 训练

uv run train Mjlab-Bow-Flat-MicroDuck --env.scene.num-envs 4096

5.4 发布

uv run publish --task Mjlab-Bow-Flat-MicroDuck \
    --wandb-run-path <...> \
    --repo /microduck-bow \
    --kind episodic --duration-s 3.0

5.5 真机加载

sudo robotctl policy add bow /microduck-bow
robotctl robot do bow   # 触发鞠躬

不需要改 daemon 代码——manifest 描述了一切。

8. 一句话总结

鸭子的"多动作"是 N 个独立 ONNX + 一个 daemon 状态机。 训练时一次训一个，发布时各发各的，运行时按 slot 切换。 想加新动作 → 训一个新任务 → 发一个新 ONNX → 装到新 slot。
