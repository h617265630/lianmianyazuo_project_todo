07 · 打通软硬件 + RL 的任督二脉

核心论点：通过 Microduck 这一个真实项目，把"硬件 + 软件 + 强化学习"三层从抽象名词变成可改的代码行。

1. 为什么"打通"很难 —— 三类典型困境

困境典型表现仓库里的破局点
纯软件 → 不会硬件调一周 reward，仿真走稳，到真机跌倒friction_dr_bam.py 把电压-电流-摩擦显式建模
纯硬件 → 不会 RL能 PWM 控制 SG90，但不知策略怎么训microduck_velocity_env_cfg.py 把 task 用 dataclass 拆开
纯 RL → 不会落地HalfCheetah 训得不错，但 ONNX 怎么上板没碰过export.py + publish/cli.py 把 train → ONNX → HF Hub → robotctl load 画成 4 条命令

3. 三层的具体交集点（核心表）

交集触点文件一句话解释
硬件 → RLactuator/friction_dr_bam.pyBAM 把"电压→电机力矩→摩擦预算"封装成 RL 可见的扭矩
硬件 → RLrobot/microduck_constants.py_BAM_ACTUATOR_KWARGS 里 vin_range=(6.5,8.2) 把电池电压波动烤成 DR
软件 → RLmicroduck_velocity_env_cfg.pyenv cfg 把 reward 按 dataclass 调权重；改任何一项都是改"RL 在优化什么"
RL → 硬件export.py注释明写"normalizer 烤进 ONNX = actor(normalizer(obs))"；手转 checkpoint = 仿真正常、真机全废
RL → 硬件scripts/infer_policy.pyBAM_MOTOR_NAME / BAM_VIN_RANGE / BAM_KP_FW 必须与训练侧一致

4. 7 步打通路线（每步带练习 + 产出物）

  1. 步 1：会用 MuJoCo viewer（Week 1–2）
    做：uv sync + uv run list-envs；打开 scene.xml；infer_policy.py 按 WASD/IJKL
    产出：notes/步1.md 记录鸭子第一次倒下的帧
  2. 步 2：改一个 reward（Week 3–4）
    做：microduck_velocity_env_cfg.py:289 pose.weight 1.0 → 1.5，跑 5-iter smoke
    看：Episode_Reward/pose 是否 ≤ 0
  3. 步 3：加一个新传感器（Week 5–6）
    做：在 cfg.scene.sensors 元组里加 ContactSensorCfg
  4. 步 4：用真实伺服校准 BAM（Week 7–8）
    有真 XL330：跑 validate_bam_testbench.py，对齐 params/xl330/m6_new.json
  5. 步 5：训一个简单任务（Week 9–10）
    做：5-iter smoke → 4096 env 跑 1000 iter
  6. 步 6：部署到真机（Week 11–12）
    做：export.py → publish → robotctl policy load
  7. 步 7：端到端调通（Week 13–16）
    做：发现"真机会向后倒" → 检查 IMU 偏置（runtime 里设置）
