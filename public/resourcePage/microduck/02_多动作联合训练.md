# 02 · 多动作联合训练 —— 怎么让鸭子会很多事

> 核心答案：**每个动作是一个独立的 ONNX 策略，运行时由 daemon 按 slot 切换。**
> 这不是"一个网络搞定一切"，而是"多个专家，编排层做调度"。

---

## 1. 先纠正一个直觉偏差

新人最容易问的问题：

> "能不能训一个大网络，什么都会？"

技术上可以（multi-task / hierarchical RL / skill primitives），但**工程上
当前不是这么做**。原因是：

1. **训练变慢很多**——多个任务共享表征会互相干扰（task interference）
2. **sim2real 难度爆炸**——失败模式叠加，调试极其痛苦
3. **算力不划算**——鸭子只有 RK3566（4×A55），单策略 50 Hz 推理已经吃紧

Pollen Robotics 选择的工程方案：**每个动作训一个 ONNX，运行时做切换**。
这就是为什么 `microduck` 机器人出厂带 7 个独立策略。

---

## 2. 官方动作 / 槽位表

来自 `src/mjlab_microduck/publish/manifest.py` 的 `SLOTS` 常量：

```python
SLOTS = ("walk", "stand", "sitstand", "ground_pick",
         "kick_left", "kick_right", "roulade")
```

| Slot | 含义 | 任务 ID | kind |
|---|---|---|---|
| `walk` | 走路（默认） | `Mjlab-Velocity-Flat-MicroDuck` | perpetual |
| `stand` | 站立 | （专用的站立任务） | perpetual |
| `sitstand` | 坐 ↔ 站（按命令切换） | `Mjlab-SitStand-Flat-MicroDuck` | perpetual |
| `ground_pick` | 用嘴捡东西 | `Mjlab-GroundPick-Flat-MicroDuck` | episodic |
| `kick_left` | 左脚踢球 | `Mjlab-BallKick-Flat-MicroDuck` | episodic |
| `kick_right` | 右脚踢球 | `Mjlab-BallKick-Flat-MicroDuck` | episodic |
| `roulade` | 前滚翻 | `Mjlab-Roulade-Flat-MicroDuck` | episodic |

每个 slot 由独立的 PPO 训练得到，权重是一个 ~MB 级别的 ONNX。

---

## 3. `kind` 字段：episodic vs perpetual

manifest 里有个关键分类（`Kind = Literal["episodic", "perpetual"]`）：

### perpetual（永久性的）
- **没有终止时间**，一直跑直到 daemon 让它停
- 走路 / 站立 / sitstand 都是这种
- daemon 把它们**装到 slot 里**，`robotctl policy load walk <repo>` 就是把
  walk.onnx 装到 walk slot
- 走路策略可以一直跑，因为它本质是个"稳态控制"

### episodic（一次性的）
- **有时间限制** `duration_s`，到时间自己停
- 踢球 / 滚翻 / 捡东西都是这种——它们有起手式 + 收势，做完必须让位
- daemon 用 `robotctl robot do <name>` 触发
- 内部还有个 `chain` 标志：按住按钮时是否连续触发（roulade 是，kick 不是）

### 额外：unwind_s
- 用于"perpetual + 收势"的混合：比如"保持金鸡独立姿势"，`unwind_s` 告诉
  daemon 收回时怎么安全过渡回 walking 策略

> 一句话区分：**走路是 perpetual，技能是 episodic**。

## 4. 多个 ONNX 在运行时是怎么"联合"起来的

鸭子不是"一个大脑"，而是"一窝专家 + 一个调度员"。

```
┌─────────────────────────────────────────────────────────────┐
│  robotd (Rust daemon, 50 Hz)                                  │
│                                                              │
│  ┌──────────┐    policy_id    ┌──────────────────────────┐   │
│  │ Scheduler │ ──────────────▶ │ 当前激活的 ONNX 推理     │   │
│  │ (state    │                 │ (单线程 onnxruntime)    │   │
│  │  machine) │ ◀──────────────  │                         │   │
│  └──────────┘    ctrl[14]     └──────────────────────────┘   │
│       ▲                                  ▲                   │
│       │ gamepad / NFC / voice / app      │ obs[61]           │
│       │                                  │                   │
└───────┼──────────────────────────────────┼───────────────────┘
        │                                  │
   [User Input]                       [Sensors]
```

**几个关键事实**：

1. **同时只跑一个 ONNX**——切换是瞬时的，不是 blend
2. **切换走"先到位再切"的协议**——上一个策略把姿态收完，下一个策略从
   站立姿态接过去（这就是为什么 episodic 都有 `duration_s`）
3. **观测是 61D 共享的**——这是 manifest 强制要求的硬约束（`OBS_LEN = 61`）
4. **切换由 daemon 决定，不是策略之间协调**——简单可靠

所以"联合"不在训练里完成，而在 daemon 里完成：**预先训好 N 个专家，运行时
按事件触发切换**。

## 5. 自己加一个新动作的完整流程

假设你想加一个"鞠躬"动作。

### 5.1 写任务配置

在 `src/mjlab_microduck/tasks/` 加 `microduck_bow_env_cfg.py`，模仿 `microduck_standup_env_cfg.py`：

```python
# 关键三件套：观测 + 奖励 + 终止
@configclass
class MicroduckBowEnvCfg(MicroduckBaseEnvCfg):
    def __post_init__(self):
        super().__post_init__()
        # 起始姿态：站立（HOME）
        # 目标姿态：躯干前倾 45°，维持 0.5 s
        # 奖励：靠近目标的 Gaussian + 头不撞地 + 不倒
        # 终止：超时 / 撞地
        # 时长：3 s
```

### 5.2 注册

在 `tasks/__init__.py` 加一行：

```python
register_mjlab_task(
    task_id="Mjlab-Bow-Flat-MicroDuck",
    env_cfg_entry_point="...MicroduckBowEnvCfg",
    ...
)
```

### 5.3 训练

```bash
uv run train Mjlab-Bow-Flat-MicroDuck --env.scene.num-envs 4096
```

### 5.4 发布

```bash
uv run publish --task Mjlab-Bow-Flat-MicroDuck \
    --wandb-run-path <...> \
    --repo <you>/microduck-bow \
    --kind episodic --duration-s 3.0
```

### 5.5 真机加载

```bash
sudo robotctl policy add bow <you>/microduck-bow
robotctl robot do bow   # 触发鞠躬
```

不需要改 daemon 代码——manifest 描述了一切。

## 6. 一个真机的"复合动作"例子

"鸭子看到人来 → 歪头打量 → 走近 → 鞠躬"

在这个体系下，编排发生在**外部脚本**（或者更上层应用）：

```python
# 伪代码
def greet():
    trigger_skill("head_tilt")          # 1. 歪头（episodic, 1s）
    time.sleep(1.0)
    set_velocity_slot("walk", vx=0.2)   # 2. 慢走近
    time.sleep(2.0)
    set_velocity_slot("walk", vx=0.0)   # 3. 停
    time.sleep(0.5)
    trigger_skill("bow")                # 4. 鞠躬
```

**鸭子在底层永远只做一件事**：跑当前激活的 ONNX。"复合"是上层调度。

## 7. 学术上的"统一多动作"方案（暂未采用）

如果你将来想做"一个网络会 7 件事"，主流方案有：

| 方法 | 思路 | 鸭子上的可行性 |
|---|---|---|
| **Hierarchical RL** | 高层策略选 subgoal，低层执行 | 算力吃紧，难 |
| **Skill primitives + RL** | 训 7 个 skill + 1 个路由器 | 中等，但 sim2real 难调 |
| **Multi-task single net** | 一个网络 7 个 head | 任务干扰，调试地狱 |
| **Distillation** | 把 7 个专家蒸馏成 1 个 | 容量可能不够 50 Hz |
| **Mixture-of-Experts** | 路由 + 多个子网络 | 推理贵 |

**当前工程的判断**：鸭子体量太小，算力只够"切策略"。但你可以尝试一个
**简化版**：把多个 slot 的策略蒸馏成一个 ONNX，用一个相位变量（phase /
posture flag）作为输入维度——`02_多动作联合训练.md` 末尾可以做为进阶实验。

---

## 8. 一句话总结

> **鸭子的"多动作"是 N 个独立 ONNX + 一个 daemon 状态机。**
> 训练时一次训一个，发布时各发各的，运行时按 slot 切换。
> 想加新动作 → 训一个新任务 → 发一个新 ONNX → 装到新 slot。
