# 08 · 如何阅读这个项目 —— 给新人的 4 周入门路径

> 写给第一次打开 `microduck_rl/` 仓库的人。
> 这份文档不重复 `AGENTS.md`（那是写给 AI Agent 的 sim2real playbook）和 `README.md`
> （那是命令速查），它回答的是一个更基础的问题：**我应该先读哪一份代码，按什么顺序读，
> 读的时候盯着什么看？**

读完任何一段代码，请把"我看到了什么"扔进 `duck_分析/notes/`，模板见
`duck_分析/notes/README.md:1-27`。

---

## 0. 这是一篇**师兄视角**的导读

我在仓库里挖了一圈以后，给你画一张心智地图。它有五层，每层只关心自己的事：

| 层 | 关心的对象 | 在仓库里的入口 |
|---|---|---|
| **L0 · 物理与仿真** | MJCF / MuJoCo / BAM | `src/mjlab_microduck/robot/microduck/*.xml` |
| **L1 · 环境** | env_cfg / mdp 函数 / DR | `src/mjlab_microduck/tasks/*.py` |
| **L2 · 训练** | PPO / rsl_rl / runner | 间接：mjlab 包，触发点在 `train_cli.py` |
| **L3 · 导出与发布** | ONNX / manifest / Hub | `src/mjlab_microduck/export.py`、`publish/` |
| **L4 · 真机** | daemon / robotd / updater | 不在这个仓库！在 `pollen-robotics/microduck` |

下面分别说每一层是什么、读哪几个文件、盯着什么看。

---

## 1. 整体代码地图（按依赖关系分层）

### Layer 0 · 物理与仿真（先有身体，再有脑子）

#### 1.1 MJCF 模型 — `robot_walk.xml` / `robot_groundcontact.xml`

机器人在 MuJoCo 里就是一份 XML。`src/mjlab_microduck/robot/microduck/robot_walk.xml:1` 是
walking 任务用的精简版（只保留脚底接触，去掉躯干/头接触 — 跌倒成本低，鼓励学走路）；
`robot_groundcontact.xml` 是地面接触全集，给 standup / sitstand / ground pick / roulade 用。
`robot_groundcontact_rollers.xml` 给 roller 滑冰家族 — 4 个 passive 轮关节。

读 `robot_walk.xml:1-40` 你会看到 5 类 default 类目（`microduck`/`visual`/`collision` +
四个历史 actuator 实验档）。这一行 `<position kp="50" dampratio="1"/>` 是给"看模型用的 XML
PD"留的备份；真正训策略的 actuator 来自 BAM，不在 XML 里 — 见 Layer 1 的 `BAM` 配置。

读 `additional.xml` / `joints_properties.xml` / `sensors.xml` 知道"额外的关节属性"和
"传感器"都在另外 include 进来的文件里 — Onshape 导出器风格。

#### 1.2 Scene — `scene.xml` / `scene_walk.xml` / `scene_rollers.xml`

`scene.xml:1-58` 把 `robot_groundcontact.xml` 包一层地板 + 灯光 + 4 个 keyframe
（`INIT`、`STAND`、`SIT`、`FOLD`）。其中 `STAND` keyframe 是关键的 STAND2 pose
（`scene.xml:30-40`）——髋 26.24°、膝 0.28°、踝 25.95°，重心前移 5 mm 把 CoM 压在踝轴
上。这个 5 mm 的微调在 `AGENTS.md` 的 reward design 章节里被反复点名。

`scripts/infer_policy.py:21-26` 里硬编码的几个常量路径指的就是这些 scene 文件。

#### 1.3 BAM 物理 — `src/mjlab_microduck/actuator/friction_dr_bam.py`

这是全仓库最硬的一层。BAM 是 Rhoban 团队的电压控执行器模型（XL330），比 MuJoCo 内置 PD
真实得多。`friction_dr_bam.py:28-47` 给 BAM 加了一个 `friction_scale` 通道，每 env 一次
episodic 重置时不累积（行 14-16 的 docstring 强调）。`BacklashEncoderBamActuator`（行
64-104）则把 firmware PD 闭合点从 `qpos[main]` 改到 `qpos[main] + qpos[backlash]`，
对应"真实伺服编码器在齿轮间隙输出侧"的硬件事实 — `backlash.py` 里有更详细的物理解释。

读完这段要知道两件事：
1. 这个 actuator 是**继承** `bam.mjlab.BamActuator` 的子类（行 24），不是从零写；
2. 摩擦 DR 只能改 BAM 的 friction budget，**改不了** MuJoCo 的 `dof_frictionloss` —
   因为行 4-6 写明 BAM 在 `edit_spec` 里把 `dof_frictionloss` 清零了。

#### 1.4 关键常量 — `src/mjlab_microduck/robot/microduck_constants.py`

- 路径常量在 `microduck_constants.py:16-44`，8 个 XML 都点名（walk / groundcontact /
  allcollisions / ball / groundcontact_rollers / 三个 backlash 变体）。
- `HOME_FRAME`（行 85-109）就是 scene 里 STAND keyframe 的**字典化版本**，写明 14 个
  伺服的初始弧度。注释解释了 STAND2 的来历：旧的 HOME 让 CoM 偏在踝轴后 ~5 mm，policy
  学会用"低头"补偿。
- `BACKLASH_HOME_FRAME`（行 166-169）是更聪明的一招：把 `r".*_backlash$": 0.0` **放在
  dict 的最前面**，利用"正则 first-match-wins"，否则 unanchored 的 `r".*hip_yaw.*"`
  会跑去初始化 backlash joint（±1° 限位会被瞬间打爆）。
- `actuators`（行 132-145）是训练侧 BAM 配的来源 — `vin_range=(6.5, 8.2)` /
  `delay_min_lag=3` 都在这。回测试 `tests/test_infer_policy_bam.py` 是为这些数字
  锁的 — `scripts/infer_policy.py:33-45` 复述了一遍，但**故意不 import** 那个常量，
  避免 ~16 s 的 mjlab/warp 拖慢 CPU 推理脚本。
- `MICRODUCK_*_ROBOT_CFG`（行 171-262）是 5 个 `EntityCfg`，每个把 spec 函数、
  init_state、collision、actuator 绑在一起。

### Layer 1 · 环境（env / mdp）

#### 1.5 任务注册表 — `src/mjlab_microduck/tasks/__init__.py`

读这个文件要知道两件事：
1. **`maybe_submit_to_hf_jobs()` 在第 7 行最先跑**（行 1-7 注释） — 这是
   `--hf-jobs` 拦截的入口。详见 `train_hook.py:47-64`。
2. 第 81-234 行是 22 个 `register_mjlab_task` 调用：基类任务 11 个（Velocity / VelStand /
   StandUp / SitStand / GroundPick / BallKick / Rollers / Swizzle / RollerCrouch /
   RollerSlope / RollerStandUp / Spin / Roulade）+ 第 254-278 行的 14 个 `-Backlash-`
   变体（`tasks/__init__.py:254-270` 那个表）。**每一个变体都通过
   `make_backlash_variant()` 包裹**。

#### 1.6 入口 cfg — `microduck_velocity_env_cfg.py`

这是"主任务 + 其他任务的共享模板"。`microduck_velocity_env_cfg.py:1-17` 的 docstring
列了 5 条该任务特有的设计决策（例如 `TURN_IN_PLACE_FRACTION = 0.15` 是为了让旋转
in-place 占 15% 的数据 — 行 25，独立均匀采样只会给出 ~2%）。

`make_microduck_velocity_env_cfg(play, rough)`（行 193-）是工厂。它先 `cfg = make_velocity_env_cfg()`
（mjlab 的速度任务模板，行 263），然后逐项 patch：
- 行 266-268：换 robot cfg、注册 contact sensor / self-collision sensor / foot height ray sensor。
- 行 277-289：pose reward 的 std / selection，行 286 的正则 `^(?!passive_|.*neck.*|.*head.*).*`
  显式把 neck/head 从 pose reward 里拿出去 — 因为它们由 head_pose_tracking 接管，
  否则两路 reward 会打架（行 281-284 注释）。
- 行 292-301：upright reward 从 weight 1.0 翻到 2.0、std 从 0.1 改成 `sqrt(0.05)` —
  `microduck_velocity_env_cfg.py:294-299` 写了为什么（前倾 4° 时旧权重几乎免费）。
- 行 314-315：foot_slip 故意留 `-0.1`（不是 `-1.0`），因为鸭子转弯太重脚。
- 行 317：去掉 stock 的 `soft_landing` reward。

读完这段你应该看到"reward 是一组**带名字的 dataclass**，每个 term 可以单独配 weight
和 params；cfg 树是 mjlab 的 ManagerBasedRlEnvCfg 大类的一棵 patch"。

#### 1.7 MDP 函数库 — `src/mjlab_microduck/tasks/mdp.py`

**7188 行、230 个函数**，是全仓库最大的文件。分三大块：

1. **行 1-66：NaN 守门员**。三处 monkey-patch：
   - 行 32-40：覆盖 `RewardManager.compute`，所有 reward 求和前 `nan_to_num`。
   - 行 52-58：覆盖 `PPO.compute_returns`，advantage 标准化前 `nan_to_num`。
   - 行 60-64 注释：第三处（ActorCritic std clamp）已在 mjlab 1.3.0 移除。
   为什么需要：`mdp.py:24-29` 写明 mjlab 在 reset **之前**算 reward，NaN 物理状态会
   一路传到 PPO loss → gradient → `torch.normal` 崩。

2. **行 76-123：ONNX exporter 元数据修正**。`microduck` 新模型有 passive 关节（喙连杆
   用 equality constraint 闭合，没有 XML actuator），upstream exporter 会 KeyError —
   所以 `_get_base_metadata_no_passive`（行 79-）在导出前把 passive joint 过滤掉。

3. **行 125 起：真正的 mdp 函数**。`grep -n "^def " src/mjlab_microduck/tasks/mdp.py`
   能看到全 230 个名字。新人先盯三类：
   - `_fallen_mask`（行 507-524）：用一个 z + cos(tilt) 阈值的 mask 标记跌倒；
   - `upright_progress`（行 546-572）和 `height_progress`（行 575-601）：
     potential-based shaping，`Δcos(tilt)` 和 `Δz` — **pay 进步不 pay 状态**，是 AGENTS.md
     "永远不要在坏状态上挂正 reward"那一条的具体实现；
   - `joint_pos_limit_proximity`（行 1989-）：qpos 侧的限位邻近惩罚 —
     `AGENTS.md` 里"关节能卡硬限位"那条坑的修复。

   其他的你可以**先用 grep 找名字，看到再读**。

#### 1.8 Backlash 变体 — `src/mjlab_microduck/tasks/backlash.py`

92 行的胶水。`make_backlash_variant(cfg, robot_cfg)`（行 42-92）做三件事：
1. 替换 robot cfg（行 47）；
2. 把 `joint_pos` / `joint_vel` obs 换成 `joint_pos_rel_backlash` /
   `joint_vel_rel_backlash`（行 49-65）— 这两个 mdp 函数把 qpos[backlash] 加到
   qpos[main] 上；
3. 收紧 `dof_pos_limits` reward 的 asset_cfg 到 `_SERVO_JOINTS_ONLY`（行 39 +
   行 68-72），否则 backlash 关节一出生就骑在 ±1° 限位上会一直挨罚。
   `backlash.py:81-90` 还会把 pose reward 的 joint 正则前缀加上 backlash 排除 —
   防止"passive_left_hip_yaw_backlash" 同时被 `.*hip_yaw.*` 和 `.*passive_.*` 选中。

### Layer 2 · 训练（PPO / rsl_rl）

#### 1.9 训练入口 — `train_cli.py` + `train_hook.py`

这俩文件只有 ~100 行，但是故事很精彩。`train_cli.py:1-18` 注释说"我们必须一直
**声明** 一个 `train` 脚本，即使它和 mjlab 的一模一样"。原因：同名 console script 是
last-writer-wins；删了我们这边的 wrapper 反而会把 mjlab 的也带进卸载名单（uv 装的
RECORD 互相覆盖），下一句 `uv run train` 找不到 `train`，PATH 上有啥就调啥 —
历史上调到过 liblinear 的 `train`（`train_cli.py:13-14` 注释）报
`can't open input file Mjlab-Velocity-Flat-MicroDuck`。

`train_hook.py:1-22` 解释 `--hf-jobs` 是怎么"既不在我们 wrapper 里实现，又
**永远不会被任何安装顺序抢走**"：通过 `mjlab_microduck.tasks` 的 import 副作用
（`tasks/__init__.py:7`），被 mjlab 自己的 plugin loader 拉到我们这边来执行。

读这两个文件主要理解两个工程教训：(a) console script 名字是稀缺资源，(b) 拦截
"mjlab 命令行 flag"的最稳通道是它的插件入口。

训练算法本身（PPO、rsl_rl）在 `mjlab` 包里，我们这边不重写。`MicroduckOnPolicyRunner`
（`tasks/__init__.py:13-23`）只覆写一行 — 把 symmetry cfg 里的 `_env` 引用剔掉再 dump
yaml（MjSpec 不可 pickle）。

### Layer 3 · 导出与发布（ONNX / manifest）

#### 1.10 导出 — `src/mjlab_microduck/export.py`

**311 行**。`run_export(task_id, cfg)`（行 72-277）做四件事：
1. 行 73-78：选 device（cuda:0 if available），加载 env_cfg + agent_cfg；
2. 行 152-200：解析 checkpoint 来源 — wandb / 本地 / `--checkpoint N` 三种；
3. 行 209-249：建 env（`ManagerBasedRlEnv`），套 `RslRlVecEnvWrapper`，实例化 runner，
   `runner.load(...)` 灌权重，`runner.get_inference_policy()` 拿到一个推理 policy；
4. 行 252-267：调 `runner.export_policy_to_onnx(...)`（mjlab 1.3.0 内部已把 normalizer
   烘到图里），再调 `attach_metadata_to_onnx` 写 joint_names / stiffness / damping / default_jp。

`scripts/export.py` 是它的 11 行壳子（`scripts/export.py:1-11`）— 命令行 wrapper 把
tyro 拆出来的 cfg 喂给 `mjlab_microduck.export.main`。

注意：`export.py:1-9` 的 docstring 把这条路径称为"the ONE path from a checkpoint to a
deployable `.onnx`"。在模拟器里 play 时 normalizer 也会被自己应用，
所以手转的 ONNX 看起来跑得对、到机器人上就废。

#### 1.11 Manifest — `src/mjlab_microduck/publish/manifest.py`

**386 行，没有 mjlab / torch import**（行 9-11）— 故意让测试在笔记本上毫秒级跑完，
让 CLI 在没有 GPU 的环境也能验证一个 ONNX 文件。

- 行 22-31：常量 — `SCHEMA_VERSION = 2`、`OBS_LEN = 61`、`ACTION_LEN = 14`、
  `POLICY_FILE = "policy.onnx"`、`SLOTS` 七种 daemon 槽位。
- 行 47-61：`Provenance` dataclass — `commit` / `branch` / `dirty` / `run` / `checkpoint`。
- 行 68-86：`git_provenance()` 在仓库里 `git rev-parse` 拿这三个字段；不在 git 里就返回 `{}`。
- 行 89-182：`build_manifest(...)` 构 dict。
- 行 185-218：`validate_manifest(manifest)` — 严格按 daemon 的拒绝条件检查。
  `manifest.py:197-198` 检查 `obs_len == 61`，`manifest.py:199-200` 检查
  `action_len == 14`，任何一项不等于就抛 `ManifestError`。
- 行 233-261：`inspect_onnx(path)` — 读 .onnx 的 input/output shape。
- 行 279-310：`smoke_run_onnx(path, steps=50)` — 跑 50 步拒绝 NaN / 常数输出。

`src/mjlab_microduck/publish/cli.py:33-86` 是 `PublishConfig` dataclass — 全是 kw-only
字段，tyro 自动生成 CLI。`cli.py:143-219` 的 `run(cfg)` 是流水线：解析权重 → 校验
ONNX → smoke run → 写 manifest → 写 README → Hub upload → `cli.py:90-92` 的
`_fail()` 在每一步报错。

### Layer 4 · 真机（daemon / robotd）

不在这个仓库里。仓库头几行的 docstring 就指向
`github.com/pollen-robotics/microduck`。但是 — 你需要知道它存在：

- `src/mjlab_microduck/sim/__init__.py:1-7` 写明 `body_server.py` 是"sim-side 那一半
  `robotd --sim`"：MuJoCo 持身体，daemon 持一切别的东西，socket 替代 servo 总线。协议在
  microduck 仓库的 `docs/design/simulation.md`。
- `publish/manifest.py:1-7` 注释直接点了 daemon 的位置：
  `updater/src/policy.rs` 和 `robotd-params` 是"读 manifest 那一边"。
- `manifest.py:38-39` 七个 slot（`walk`/`stand`/`sitstand`/`ground_pick`/`kick_left`/
  `kick_right`/`roulade`）就是 daemon 那一侧的命名。

新人不要一上来就跳到 L4，先把 L0-L3 都读通，知道"为什么 manifest 是这个形状"再
读 daemon 不迟。

## 2. 推荐 4 周阅读计划（每天 1-2 小时）

> 这一节是**具体到小时**的路径。每个 stage 末尾我都给了"如何检验自己读懂"的信号，
> 不必都要做，至少做 1-2 个。

### Week 1 · 把 MuJoCo 那层吃透

#### Day 1-2 · MuJoCo + `scene.xml`

- 装一个 MuJoCo viewer（`uv run mujoco.viewer` 或直接 `uv add mujoco` 后 python
  打开），加载 `src/mjlab_microduck/robot/microduck/scene.xml`。
- 用 keyframe `STAND`（`scene.xml:30-40`）让模型站立，看清楚 14 个伺服。
- 顺便加载 `SIT` 和 `FOLD`，观察关节角度差异。
- 检验：你能口头说出 14 个 joint 的索引顺序（左腿 0-4、颈头 5-8、右腿 9-13）。

#### Day 3-4 · `robot_walk.xml` 与 14 DOF

- 通读 `robot_walk.xml:1-40` 的 default 段；明白 `<position kp="50" dampratio="1"/>`
  这一行**不参与训练**。
- 读 `microduck_constants.py:85-109` 的 `HOME_FRAME`，对照 `scene.xml:30-40` 的
  STAND keyframe：每个数字必须对得上。
- 用 `mujoco.MjSpec.from_file(...)` 写一个小脚本，把 14 个 joint 的 name / range 打印出来。
- 检验：你能默写 14 个 joint 名字 + HOME 弧度（精确到 0.01 rad）。

#### Day 5-7 · BAM actuator

- 通读 `friction_dr_bam.py:1-100`（先看 docstring 行 1-16）。
- 在 IPython 里 `from bam.model import load_model; bam = load_model(motor_name="xl330",
  model="m6"); print(bam.actuator.kp, bam.actuator.vin)`。
- 看 `microduck_constants.py:132-145` 训侧 BAM kwargs，理解 `vin_range` /
  `vin_drop_gain_range` / `vin_min` 各自的物理含义。
- 检验：你知道"为什么 friction DR 不能用 mjlab 的 `dr.dof_frictionloss`"。

### Week 2 · 把 env / mdp 这层读通

#### Day 1-3 · `microduck_constants.HOME_FRAME`

- 重读 `microduck_constants.py:85-109`，把每条正则 + 数值抄到 notes 里。
- 注意行 87-92 注释解释 STAND2 的来历 — 这是"为什么 5 mm 重要"的代表性例子。
- 看 `BACKLASH_HOME_FRAME`（行 166-169）的"first-match-wins"技巧 —
  自己写一个 Python 脚本模拟 dataclass 替换，验证 dict 顺序对结果的影响。
- 检验：你能向一个新人解释"正则 first-match-wins 是怎么救命的"。

#### Day 4-5 · `mdp.py` 主要函数

- `mdp.py:32-58` 的两个 NaN patch — 画个调用栈图：
  `step()` → `RewardManager.compute()` → `nan_to_num` → `PPO.compute_returns()` →
  `nan_to_num`。
- `mdp.py:507-572`：`upright_progress` 和 `_fallen_mask`。这一对是"potential-based
  shaping"的范式。
- `mdp.py:1989-`：`joint_pos_limit_proximity` — 为什么 stock `dof_pos_limits` 不够。
- 检验：你能说出"potential-based shaping 为什么不 farmable"。

#### Day 6-7 · `microduck_velocity_env_cfg.py`

- 通读 `microduck_velocity_env_cfg.py:1-169`（开头常量段）和行 193-400（factory 函数）。
- 重点对照 `microduck_velocity_env_cfg.py:286` 的 joint 正则和 `mdp.py:507-524`
  的 `_fallen_mask` 的 mask — 它们是同一个"先排除 passive"的哲学。
- 自己写一个 diff：把 `microduck_velocity_env_cfg.py:300-301` 的 `upright.weight=2.0,
  std=sqrt(0.05)` 改成 `1.0, 0.1`，跑 smoke test 看看 warning。
- 检验：你能闭着眼睛讲完"pose / upright / foot_slip / action_rate 这四个 reward
  的 weight 取值和原因"。

### Week 3 · 训练、导出、发布

#### Day 1-3 · rsl_rl 训练流程

- 不需要读 rsl_rl 的源码（那是 mjlab 的依赖）。读懂 `tasks/__init__.py:13-23` 的
  `MicroduckOnPolicyRunner`。
- 跑 `uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 64
  --agent.max_iterations 5`（AGENTS.md 推荐的 smoke test），看 wandb 面板上的
  `Episode_Reward/*` 是不是全 ≤ 0（AGENTS.md 的 infallible check）。
- 检验：你能解释 `--hf-jobs` 是怎么在 `tasks/__init__.py:7` 的 import 副作用里被

#### Day 4-5 · `export.py`

## 6. 阅读时容易迷路的地方

这五处都是新人常见的"我读懂了其实没读懂"陷阱，提前警告。

### 6.1 mjlab vs microduck_rl 的边界

**microduck_rl 是 mjlab 的下游消费者**。`tasks/__init__.py:1-22` 里
`register_mjlab_task` 来自 `mjlab.tasks.registry`，PPO 来自
`rsl_rl.algorithms.ppo`，rewards 框架来自 `mjlab.managers`。

新人常见错：花一周读 mjlab 的 `ManagerBasedRlEnv` 源码。**先读 microduck 这边怎么用**，
再回头看 mjlab 那一层为什么这么设计 — 倒过来读效率高三倍。

### 6.2 dataclass 嵌套 dataclass 难以追踪

`microduck_velocity_env_cfg.py` 里 `cfg.rewards["pose"].params["asset_cfg"]` 是个
`SceneEntityCfg`，它又有 `.joint_names` 一个 tuple of regex。这条链**至少三层**，光用
编辑器很难跟踪。

实战技巧：

```python
import dataclasses
print(dataclasses.asdict(cfg.rewards["pose"]))
```

或者在 IPython 里：

```python
from mjlab_microduck.tasks import mdp as microduck_mdp
from mjlab_microduck.tasks.microduck_velocity_env_cfg import (
    make_microduck_velocity_env_cfg,
)
cfg = make_microduck_velocity_env_cfg()
print(cfg.rewards.keys())
print(cfg.rewards["pose"])
print(cfg.rewards["pose"].params["asset_cfg"].joint_names)
```

### 6.3 DR 函数 vs 任务 cfg 的区分

`microduck_velocity_env_cfg.py:30-87` 一堆 `ENABLE_*` 是**开关**；同文件行 36 提到的
`JOINT_FRICTION_RANDOMIZATION_RANGE = (0.9, 1.1)` 是**范围**；实际生效的事件函数在
`mdp.py` 里（搜 `randomize_bam_friction` 等）。

新人常错：以为改 `JOINT_FRICTION_RANDOMIZATION_RANGE = (0.5, 0.5)` 就 DR 不变了 —
其实那是范围的两端，都设成 0.5 是把摩擦锁死在 50%，比"不开"还糟。

### 6.4 注册表机制（`register_mjlab_task`）

`uv run list-envs` 是怎么知道有哪些 task 的？因为 `tasks/__init__.py:81-278` 在 import
时把所有 task 注册到 `mjlab.tasks.registry.REGISTERED_TASKS`。这个注册表是**模块导入
副作用**，不是某个 `config.yaml` 配出来的。

新人常错：在 `tasks/__init__.py` 加了 register 但忘记 import — `uv run list-envs` 看不到。
**所有 register 必须在文件顶层调用**，不能放进 `if __name__ == "__main__":`。

### 6.5 ONNX metadata 是怎么"嵌进去"的

`export.py:266-267` 调 `attach_metadata_to_onnx(onnx_path, metadata)` —
这个 metadata 不是 ONNX 的标准字段，是 mjlab 自定义的 protobuf extension，存在
`model.graph.node[0].attribute` 里。`scripts/infer_policy.py` 不读它，
但 microduck daemon 那一侧会读。

新人常错：以为 metadata 是写在一个 `.json` 旁的。**它是嵌在 .onnx 内部的**。

## 8. 写在最后

microduck_rl 仓库最有意思的不是某一段代码，而是它**每个角落都有一句注释解释"为什么
这里不能这样写"**。这些注释不是写给 review 的，是写给"六个月后回来改的自己"的。

读这个仓库最有效的姿势，不是逐行读，是带着问题读：

- "为什么这个 reward weight 是这个数？"
- "为什么这个正则要 `^(?!passive_)`？"
- "为什么这里要 monkey-patch mjlab 的 compute_returns？"

每个问题背后都有一次具体的失败（"一旦不这样做，训练就崩 / sim2real 就掉"）。AGENTS.md
是这些故事的目录；`git log` 是故事本身；代码是结局。读的时候三件对照看，最有效。

> 真正的"懂"不是把流程背下来 — 是在自己改 cfg 的时候，**能预判**"我这一改会不会踩到
> sim2real invariant"。
> 4 周之后你回头读这份文档，会发现它漏写了一半。

— 写于读完仓库第二遍之后。
