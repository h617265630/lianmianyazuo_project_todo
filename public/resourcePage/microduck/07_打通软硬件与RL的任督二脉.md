# 07 · 打通软硬件 + RL 的任督二脉 —— 以 Microduck 为唯一载体

> 面向已经能跑 smoke test、但卡在"知道这代码在干嘛、不知为什么这么写"的同学。
> **核心论点：通过 Microduck 这一个真实项目，把"硬件 + 软件 + 强化学习"三层
> 从抽象名词变成可改的代码行**，比同时追 5 个 toy 仓库更高效。

---

## 0. 主流学习路径调研结论

搜了 2025–2026 关键词（"how to learn robotics and RL"、"sim to real learning
path"、"ANYmal sim2real"、"quadruped PPO pipeline"），
[sim-to-real 综述 2025](https://www.towardsautonomy.com/p/sim2real-building-reliable-robots)
指出"仿真 99% 成功率、零样本到真机 30% 成功率"是当前最常见失败 —— 打通链路是
解药。主流路径是 ROS2 + MuJoCo/Isaac + PPO + 系统辨识四件套，但各自只解决一层。
Microduck 几乎按这套问题反向设计：BAM 电机模型（`friction_dr_bam.py:1-113`）
替代理想 PD；`scripts/infer_policy.py:33-45` BAM 常量与训练侧对齐；
`scripts/export.py:1-11` 注释写明"normalizer 必须烤进 ONNX"。

## 1. 为什么"打通"很难 —— 三类典型困境

| 困境 | 典型表现 | 仓库里的破局点 |
|---|---|---|
| **纯软件 → 不会硬件** | 调一周 reward，仿真走稳，到真机跌倒 | `friction_dr_bam.py:28-47` 把电压-电流-摩擦显式建模；`validate_bam_testbench.py:1-100` 用真实 testbench 校核 |
| **纯硬件 → 不会 RL** | 能 PWM 控制 SG90，但不知策略怎么训 | `microduck_velocity_env_cfg.py:193-340` 把"task = robot+scene+obs+reward+DR"用 dataclass 拆开 |
| **纯 RL → 不会落地** | HalfCheetah / Ant 训得不错，但 ONNX 怎么上板没碰过 | `export.py:1-11` + `publish/cli.py:1-15` 把"train → ONNX → HF Hub → robotctl load"画成 4 条命令 |

**根因**：三层知识图谱差异太大 —— 软件出身看到 `<motor>` 就晕；硬件出身看到
`surrogate loss` 就退缩；RL 出身不知 `joint_pos` 物理含义。
**Microduck 的解药**：把每层都用**一个具体文件**承载，强制它们在主线流程相遇（§3）。

## 2. Microduck 在打通链路上的位置

### 2.1 它能教

- **完整 sim-to-real pipeline**：`train → export → publish → robotctl load`
  四步闭环（`AGENTS.md` + `publish/cli.py:1-15`）
- **真实硬件物理模型**：BAM 电压 + M6 摩擦 + backlash 间隙（`friction_dr_bam.py:37-47`）
- **域随机化工程纪律**：`microduck_velocity_env_cfg.py:31-86` 顶层常量 +
  `mdp.py:3212-3240` non-accumulating 正确写法
- **真机 NaN 防护**：`mdp.py:32-58` Patch 1-2 monkey-patch mjlab 的
  RewardManager / PPO，因为训练期 NaN 会污染整个网络
- **发布协议**：`publish/manifest.py:89-185` 的 schema-2 契约（与 daemon
  `docs/policy-manifest.md` 对齐）

### 2.2 它不能教

- **ROS2 通信** —— 上层 `robotd` 在 `pollen-robotics/microduck`
- **机械 CAD / PCB** —— 鸭子本体不公开（`05_硬件实现.md:23`），只能复刻不能改造
- **量产 / 供应链** —— `05_硬件实现.md:240-260` 给了估算但非实战
- **无线部署** —— WebRTC/BLE/NFC 都在 daemon 仓库

## 3. 三层的具体交集点（核心表）

下表是本文重头戏，每行都可在仓库直接验证：

| 交集 | 触点文件 | 关键行 | 一句话解释 |
|---|---|---|---|
| **硬件 → RL** | `actuator/friction_dr_bam.py` | `:37-47` | BAM 把"电压→电机力矩→摩擦预算"封装成 RL 可见的扭矩；策略 `action` 仍是关节角目标，但仿真侧用 M6 公式算真实扭矩 |
| **硬件 → RL** | `robot/microduck_constants.py` | `:132-145` | `_BAM_ACTUATOR_KWARGS` 里 `vin_range=(6.5,8.2)` 把 NP-F550 电池电压波动烤成 DR；训练侧不能想当然写 12 V |
| **硬件 → RL** | `tasks/mdp.py` | `:3198-3210` | `expand_bam_friction_fields` 是 startup no-op，但**每个用 BAM 的 env 都必须注册**，否则 mjlab 不扩展 dof_frictionloss，DR 静默失效 |
| **软件 → RL** | `microduck_velocity_env_cfg.py` | `:193-340` | env cfg 把 `pose`/`upright`/`track_*`/`action_rate`/`air_time` 这些 reward 按 dataclass 调权重；改任何一项都是改"RL 在优化什么" |
| **软件 → RL** | `microduck_velocity_env_cfg.py` | `:382-386` | `nan_state` termination 注册 `feet_ground_contact` 传感器；没有它一次 NaN 会污染整个网络 |
| **软件 → RL** | `microduck_velocity_env_cfg.py` | `:471-498` | DR 用 `operation="add"/"scale"` 配合 mjlab 1.3.0 的 `uses_defaults=True`，**天生 non-accumulating**；自写 DR 必须显式 restore-then-apply（`mdp.py:3212-3240`） |
| **软件 → RL** | `tasks/mdp.py` | `:963-1000` | `robot_state_is_nan` 同时检查 `joint_pos/vel + root_link pos/quat/vel/wheel_vel` —— base free-joint 与被动轮都是 NaN 高发区 |
| **RL → 硬件** | `src/mjlab_microduck/export.py` | `:252-267` | 注释明写"normalizer 烤进 ONNX = `actor(normalizer(obs))`"；手转 checkpoint = 仿真正常、真机全废 |
| **RL → 硬件** | `scripts/infer_policy.py` | `:33-104` | CPU 预演；**`BAM_MOTOR_NAME / BAM_VIN_RANGE / BAM_KP_FW` 必须与训练侧一致**（`tests/test_infer_policy_bam.py` 锁住） |
| **RL → 硬件** | `publish/cli.py` | `:85-210` | `uv run publish` 强制走 ONNX shape 校验 + smoke run + manifest schema-2 校验 |
| **RL → 硬件** | `tasks/__init__.py` | `:254-278` | `_BACKLASH_TASKS` 表把"基线任务 → 加 ±1° 间隙"做 A/B 镜像，测齿隙影响而不引入其他变量 |

### 3.1 一个完整走查示例 —— "改变一个 reward"会触及哪些文件

假设你想让鸭子走路时身体倾斜得更大一些：

1. `microduck_velocity_env_cfg.py:300-301` → 改 `upright.weight` 或 `upright.std`
2. `AGENTS.md` "Sim2real footguns" 提醒：倾斜阈值要配合 `base_orientation_randomization`
3. 重跑 5-iter smoke → 1000-iter 训练
4. 看 wandb 的 `Episode_Reward/upright`（必须 ≤ 0；变正 = 被策略利用）
5. `scripts/export.py ...` → `infer_policy.py --walking out.onnx`
6. `publish --task ... --repo user/microduck-tilted-walk` 推 HF Hub

走完 6 步，你就**亲自走通了一次**硬件 ↔ 软件 ↔ RL 的闭环。

## 4. 7 步打通路线（每步带练习 + 产出物）

> 总时间 ≈ 12–16 周业余。每步产出物必须**可分享**（wandb 截图 / 推 GitHub 的
> ONNX / HF Hub repo），否则等于没做。

### 步 1：会用 MuJoCo viewer（Week 1–2）
- **做**：`uv sync` + `uv run list-envs`；打开 `scene.xml`；`scripts/infer_policy.py --walking out.onnx` 按 WASD/IJKL
- **产出**：`notes/步1.md` 记录鸭子第一次倒下的帧
- **检验**：能答"14 个 active joint 中哪些是 `passive_*`"

### 步 2：改一个 reward（Week 3–4）
- **做**：`microduck_velocity_env_cfg.py:289` `pose.weight` 1.0 → 1.5，跑 5-iter smoke
- **看**：`Episode_Reward/pose` 是否 ≤ 0（不是 = 被利用）
- **产出**：wandb run URL + 改动前后 reward 曲线对比图
- **延伸**：写新 reward `head_idle_bonus`（仿 `mdp.py:316-350` 的 `joint_accelerations_l2`）

### 步 3：加一个新传感器（Week 5–6）
- **做**：在 `microduck_velocity_env_cfg.py:267` 的 `cfg.scene.sensors` 元组里
  加 `ContactSensorCfg`（仿 `:220-232`）监测 `passive_*_wheel`
- **注意**：obs 维度变化触发 `AGENTS.md` "Obs layout is 61D" 红线，必须同步调整 obs term 列表
- **检验**：能讲清"为什么 obs 维度变了策略就不能热插拔"

### 步 4：用真实伺服校准 BAM（Week 7–8）
- **有真 XL330**：跑 `validate_bam_testbench.py`，对齐 `params/xl330/m6_new.json`
- **无真机**：对照 BAM 论文，把 `BAM_DIR` 改成公开 BAM 包路径调 M6 参数
- **看**：`validate_bam_testbench.py:60-83` `compute_m6_friction` 是否匹配仓库 BAM 模型
- **产出**：`notes/步4-校准记录.md` 含 `mse_sim_vs_real`
- **检验**：sim 与 real testbench 的 L2 误差 < 5°

### 步 5：训一个简单任务（Week 9–10）
- **做**：5-iter smoke → 4096 env 跑 1000 iter（见 `AGENTS.md` "Budgets"）
- **必须先读**：`AGENTS.md` "Sim2real footguns" 7 条 invariant，尤其是
  "DR 不能跨 reset 累加"（`mdp.py:3212-3240` 注释）
- **产出**：wandb run URL + `logs/<experiment>/`
- **检验**：`Episode_Reward/track_linear_velocity` 在最后 100 iter 单调上升

### 步 6：部署到真机（Week 11–12）
- **真机**：`scripts/export.py` → `uv run publish --task ... --repo your-name/microduck-my-walk --kind perpetual --slot walk` → `sudo robotctl policy load walk your-name/microduck-my-walk`
- **替代**：`testbench_sim2real.py` + `infer_policy.py` 走 CPU 预演
- **产出**：HF Hub repo URL + CPU 预演录屏
- **检验**：CPU 预演能跟上 `--vel-cmd-x 0.3` 持续 30 s 不跌倒

### 步 7：端到端调通（Week 13–16）
- **做**：发现"真机会向后倒" → 检查 `microduck_velocity_env_cfg.py:84` IMU 偏置
  （**`AGENTS.md` 警告：DR 是 zero-centered，不能补偿系统偏差**）→ 改 runtime 里
  的 `imu-pitch-offset`（daemon 那边设置）
- **产出**：调通前后"实测 vs CPU 预演"对比 + `notes/步7.md`
- **检验**：能向人解释"为什么真机偏差要在 runtime 修、不能在 DR 修"

## 5. 30 / 90 / 180 天计划

| 时间窗 | 目标 | 具体任务 | 每周时间 |
|---|---|---|---|
| **Day 1–30** | 把鸭子跑起来 + 改通 reward | 步 1+2+3 | 8 h |
| **Day 31–90** | 端到端跑通 1 个任务 | 步 4+5 + 1000 iter | 12 h |
| **Day 91–180** | 真机闭环（哪怕是替代品） | 步 6+7 + wiki 总结 | 15 h |

**30 天**：wandb 上画出"reward 改动让 track_linear_velocity 涨了 X%"
**90 天**：从 0 训出"会站"的 episodic 策略（`Mjlab-StandUp-Flat-MicroDuck`）
**180 天**：把训好的策略推上 HF Hub，别人能 `robotctl policy load` 直接用

> 关键：这 180 天**不是**同时追 ROS2 + STM32 + PPO 数学，而是把 Microduck 一个
> 仓库吃透。其他技能都是周边，不冲突时再学（`06_学习路线.md:182-200`）。

## 6. 常见断点及对策

| 断点 | 现象 | 对策 | 仓库里的"钥匙" |
|---|---|---|---|
| **学不动了** | 读 mjlab 文档像天书 | 别从头读 mjlab，**只读 `microduck_velocity_env_cfg.py` 引用到的** | `:115-120` 列所有 import，反向追 |
| **对不上号** | 改了 reward 但曲线没变 | 99% 是改了 `env.cfg.*` 而 manager init 时已 deepcopy；用 `env.event_manager.get_term_cfg(...)` | `AGENTS.md` "Curricula" 段第三点 |
| **对不上号 2** | obs 维度对不上 61 | 间隙/滚轮/鸟喙的被动关节会插入 qpos | `tasks/mdp.py:126-155` helper |
| **找不到 bug** | NaN 训练崩溃 | 看 `mdp.py:32-58` Patch 1-2；运行时应打印 `[mdp] Patches 1-2 active` | `:66` 行 |
| **找不到 bug 2** | 仿真好真机跌倒 | 几乎一定是 sim2real invariant 被破坏 | `AGENTS.md` 7 条 footguns |
| **导出失败** | ONNX shape 不对 | 检查 `mdp.py:79-104` Patch 4（过滤 passive 关节） | `:113` 行 |
| **publish 失败** | manifest 校验不过 | 读 `publish/manifest.py:185-372` 的 `validate_manifest` | `:373-385` 行 |
| **真机指令不响应** | WASD 按了鸭子不动 | 检查 `infer_policy.py:460-498` 的 `_update_command` flag | 整段 |
